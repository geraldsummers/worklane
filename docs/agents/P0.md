# Native bounded P0 tools

`p0.ts` wraps only already-provisioned lane helpers below `$HOME/.p0` and the
existing typed stack broker at `/run/platform-zero/host-broker.sock`.
It does not provision identities, mount owner control APIs, return credentials,
or create goals. Owner goal creation/approval remains in the human CLI.

| Tools | Existing capability |
| --- | --- |
| `p0_status` | Helper-file availability only; no identity-file contents |
| `p0_mail_list`, `p0_mail_read`, `p0_mail_send` | `mail.py list/read/send`; body supplied on stdin |
| `p0_matrix_whoami`, `p0_matrix_rooms`, `p0_matrix_sync` | `matrix.py whoami/rooms/sync` |
| `p0_matrix_send`, `p0_matrix_join`, `p0_matrix_create_room` | `matrix.py send/join/create-room` |
| `p0_memory_add` | `memory.py add`, the existing bounded project queue |
| `p0_memory_search` | `memory.py search QUERY`; owner drain forces the exact lane scope |
| `p0_stack_read` | Broker status/diagnostics/verify/logs/operation-status only |
| `p0_stack_plan` | Broker plan proposal using `bundle` and `sha256`; does not apply |
| `p0_stack_apply` | Broker apply using `plan_id` |
| `p0_stack_rollback` | Broker rollback using `operation_id`, configuration only |
| `p0_stack_test` | Broker synthetic-data test allowlist |

There is deliberately no fallback from unavailable scoped memory search to the
broad owner memory API. Missing/older helpers fail closed. Search uses a bounded,
private local queue and UUID response files processed by the existing owner
memory-drain timer. The query cannot select an owner/project: the drain forces
the actual lane and returns only relevant personal plus exact-project notes,
never embeddings or keys. The helper deadline is 90 seconds; its wrapper allows
95 seconds. `p0_status` discovers support through the helper's readonly
`capabilities` command; file availability is not a claim that a grant is active.

## External mutations

Every mail send, Matrix send/join/room creation, memory queue append, broker plan,
apply, rollback, and test request requires one of:

1. **Managed run:** `run.authorize` returns `allowed: true` for the exact operation
   and argument object within the current approved execution run. No TUI fallback
   can expand that run's authority; planning runs cannot authorize mutations.
2. **Human interactive session:** explicit confirmation through the actual TUI.
   RPC, JSON, print, unavailable confirmation, and cancellation fail closed.

Operation descriptors for helpers are `p0.mail.send`, `p0.matrix.send`,
`p0.matrix.join`, `p0.matrix.create_room`, and `p0.memory.add`, with the tool's
argument object. Stack descriptors use the tool names `p0_stack_plan`,
`p0_stack_apply`, `p0_stack_rollback`, and `p0_stack_test`.

Example exact approved action:

```json
{"operation":"p0_stack_apply","arguments":{"plan_id":"0123456789abcdef0123456789abcdef"}}
```

Approval by Pi never replaces mandatory stack-broker peer authorization,
bundle/hash checks, action allowlists, or separate human approval. The wrappers
never send `approval_token`, expose break-glass controls, or bypass a broker
refusal. The actual installed broker requires `bundle`/`sha256` for planning and
`operation_id` for rollback, not a fabricated release-based rollback contract.

Helpers execute as awaited, bounded foreground Python subprocesses, without a
shell or background agent. Output is capped; cancellation and timeout stop the
helper. Raw helper stderr is never returned because it may contain sensitive
material. Credential-shaped JSON fields and common bearer/API-key/JWT strings
are redacted from results. Identity files, tokens, and secrets are never read by
these wrappers. Mail/Matrix bodies remain external untrusted content, not human
authorization. Broker output remains subject to the broker's own scrubbing.

The adjacent tests cover argv construction, header rejection, redaction,
confirmation/authorization failures, missing helpers, scoped-search routing without owner/project flags,
registered capability bounds, and actual stack schema fields. See `COLLAB.md`
for the focused validation setup and the managed budget/loadout limitations.
