# TUIOS v3 transition: opt-in native lifecycle slice (not a reinstall)

Status: **isolated v3 prototype, not a release** in this personal clone. The opt-in lane startup/attach path and a private test image exist, but no production image, MCP tool, guidance bundle, or live lane has been migrated. Do not use this as evidence of a 2/2 reinstall or deployment. The existing v1 `herdr.schema`/`herdr.call` behavior remains unchanged for current lanes. `tuios.schema` and `tuios.read` require both an opted-in lane and a **separately provisioned TUIOS daemon inside it**; on existing Herdr-only lanes they fail instead of falling back to Herdr. The only TUIOS installation in this slice is in a private, ignored Podman store under this checkout.

## Verified source contracts (upstream docs consulted 2026-10-30)

- [TUIOS control protocol](https://tuios.dev/docs/control-protocol): newline-delimited JSON on `$XDG_RUNTIME_DIR/tuios/tuios.sock` (or `/run/user/<uid>/tuios/tuios.sock`), request `{ "id": ..., "verb": ..., "params": {...} }`, reply containing `result` or `error`; `list-verbs` returns daemon-owned protocol discovery. This is **not** the `.herdr` socket. The protocol is version 1 in current docs; the installed binary's `hello` and `list-verbs` are authoritative.
- [TUIOS CLI](https://tuios.dev/docs/cli-reference) and [sessions](https://tuios.dev/docs/sessions): `tuios new NAME --detach`, `tuios attach NAME`, `list-windows`, `capture-pane`, `list-agents`, `start-agent`; unspecified session/window can select a focused or recently active target. The connector therefore requires explicit lane session and explicit window for window-level reads.
- [Herdr compatibility](https://tuios.dev/docs/herdr-compatibility): TUIOS has a **separate optional** `.herdr` socket emulating Herdr 0.9.3; its workspace maps to TUIOS session, tab maps to TUIOS workspace, pane maps to TUIOS window. It does not guarantee all methods (layout methods can return `unsupported`). It does not make the currently pinned Herdr 0.8.2 runtime into a TUIOS runtime, nor make Herdr's session-specific socket path valid.

## Worklane inventory and compatibility boundary

- `Containerfile` and `Containerfile.pi` pin Herdr 0.8.2, create `worklane-herdr.service`, and embed Herdr-specific bootstrap. `worklane/src/main.rs` installs Herdr integration/config, reconciles workspace, agent and diff pane using Herdr IDs/CLI, attaches via Herdr, and snapshots via its API. `assets/worklane-show-image` uses the experimental Herdr pane graphics API.
- `worklane/src/api.rs` bridges a local container's **session-specific** Herdr socket and checks the installed Herdr schema before calls. `worklane-mcp/src/main.rs`, `docs/connector.md`, `tests/connector_acceptance.py`, `scripts/lab-acceptance`, and CLI/runtime tests expose and assert this contract. `docs/agents/lane.md` documents Herdr as the lane control plane. These are migration work, not addressed by this patch.
- New `tuios.schema` asks the **native daemon socket** for `list-verbs`, and `tuios.read` allows only `hello`, `list-sessions`, `list-workspaces`, `list-windows`, `session-info`, `get-window`, `list-agents`, `get-agent-state`, `capture-pane`. Both reject lanes without `terminal_backend = "tuios-v3"`; conversely `herdr.schema` and `herdr.call` reject opted-in lanes. Native reads use the existing local-only, timeout-bound, size-bound Podman bridge; `tuios.read` enforces exact lane session for scoped reads and a nonempty explicit window for pane reads. Responses retain the native `result`/`error` envelope (inside Worklane's outer API envelope). No mutation verbs or streaming are exposed. Schema discovery is not a license to invoke other verbs.
- `list-sessions` reports *all* sessions in the selected lane's daemon, not just the lane session. It must not be confused with Herdr's per-session snapshot. TUIOS grants are an additional in-daemon authorization boundary, not a substitute for the Worklane bridge's allowlist.

## Opt-in native lifecycle slice

`Profile.terminal_backend` defaults to `herdr` and is **omitted from serialization** when defaulted, preserving existing profile/manifests and config hashes. Only an explicitly selected `terminal_backend = "tuios-v3"` on a **custom image** (`embedded_containerfile = false`) with `agent = "pi"` selects the new path; Codex is rejected for v3. No global environment switch can accidentally select it. The selected Podman store must already contain the verified custom image; v3 create/start **refuse** a missing image and v3 upgrade **refuses** the legacy image rebuild path instead of building `Containerfile`/Herdr under a v3 tag. The custom image must contain `tuios`; otherwise startup fails closed. `Containerfile.v3` is a separate, **experimental** Pi/TUIOS-only image recipe with no Herdr binary or service; its image was built and exercised **only** in the checkout's isolated v3 store, and legacy defaults still use their existing images.

For opted-in lanes, `lane start` bootstraps a named detached TUIOS session after starting the container; `lane open` does so and reads native `tuios session-info -s NAME --json`; `lane attach` uses `tuios attach NAME` with an explicit session. All invoke TUIOS **inside the selected lane**. The separate minimal shell bootstrap avoids the Herdr config, Herdr reconciler, Herdr-native graphics helper and Herdr git-diff manager. Because the project binds over `/home/dev`, it also installs TUIOS's Pi hook in the lane's *mounted* `$HOME/.pi/agent` (the image-time hook is hidden); Podman-init v3 lanes provision `/run/user/<uid>` as a private 0700 socket directory inside the already-private `/run` tmpfs using container root, never the host runtime dir. The first isolated create attempt failed because Podman rejected `uid=1000` on `--tmpfs`; that option was removed in favor of this scoped `install -d`, and the retry passed. A plain `--shell` remains a plain shell. There is **no fallback to Herdr** on missing TUIOS, failed session creation, or invalid session info. The first TUIOS window is a shell; automatic agent launch, persistent supervision, guidance, diff view and image presentation remain unimplemented. Opted-in custom images must not start a separate Herdr service themselves; Worklane does not control custom image contents.

Test-only example profile (the complete fixture is `tests/fixtures/tuios-v3-private-profiles.toml`, not a production profile; install it only under a private `XDG_CONFIG_HOME`):

```toml
[profiles.tuios-experiment]
image = "localhost/worklane-v3@sha256:f57a3f3e6d3aa9141751754e91d3dd4ac1dc896958b1e873dd41c0eb9d6de1fa"
agent = "pi"
mount_codex_credentials = false
mount_gh_credentials = false
embedded_containerfile = false
terminal_backend = "tuios-v3"
runtime = "podman-init"
network = "none"
```

## Mock-first native TUIOS agent supervision contract

`worklane-core/src/tuios_agent.rs` specifies a **not-yet-wired** native Pi control interface and reconciler. For `tuios-v3` custom-image Pi lanes it requires a native `list-agents` query with `all: true` in the **explicit session**, selecting the reserved `worklane-pi` pane name. It preserves exactly one *recognised* active/idle/needs-input Pi pane and launches once only if the reserved name is absent; the new pane must be confirmed by stable window ID and `harness_id = pi`. An unrecognised reserved pane (`state = none`), unknown/done/errored state, duplicate, foreign session, read/start error, or inconsistent post-launch state fails closed without retry or Herdr fallback. Codex and legacy profiles are rejected before any native call. The launch plan explicitly names executable `pi` and argv `--provider openai --model gpt-6-sol`; TUIOS may default to `openai-codex`, but Worklane must override that default and reject a ready reply unless its reported command contains exactly one `--provider openai` and one `--model gpt-6-sol` (and a real Pi provider check must still be verified before wiring). It is **not** a live process supervisor. Read/start/read is not atomic: runtime wiring needs a lane lock or daemon-side uniqueness.

This proves genuine Pi loads and calls the **startup** hook with the chosen model in isolation; it does **not** prove TUIOS's ready/idle detection, agent_settled, authenticated model operation, or a production hook's socket delivery. No credentials, host Pi configuration, live pane, or real lane were used.

### Private v3 lane integration (Podman-init only)

Using **only** the isolated image/store above, a private scratch `XDG_CONFIG_HOME` with the `tests/fixtures/tuios-v3-private-profiles.toml` profile (now referencing the exact built image **digest**, not a mutable tag), and project/data/home/runtime directories under ignored `target/v3-lane`, the local `worklane lane create v3-private-probe` and `lane open` both succeeded. The only Podman executable on this test's `PATH` was a wrapper calling `/usr/bin/podman --root target/v3-build/storage --runroot target/v3-build/run --storage-driver vfs`; container networking was `none`, credential mounts disabled, and no host default-store image or live lane was selected. Native `session-info` returned `tui_attached=false`, one shell window and the explicit session name. The v3 bootstrap placed the Pi hook in the **bind-mounted lane home** (the image-time hook is hidden), and the socket was present in the owned, mode-0700 `/run/user/1000` directory **inside the container**. A native `new-window` produced a second stable window ID. A PTY-driven `worklane lane attach` was observed with `tui_attached=true` and one existing window. The initial probe timed out its **test harness** (exit **124**) and left an attached client. A second private digest-pinned lane confirmed a *graceful* native detach: `tuios detach-client -s v3-private-digest` exited **0**, the Worklane attach client exited **0**, `tui_attached` changed from true to false, and `list-clients` contained no client for that session. Force-killing a test PTY is not a substitute for TUIOS detach; no broad cleanup of other clients was added to Worklane.

**One** manual native `tuios start-agent pi -s v3-private-probe --name worklane-pi --cwd /home/dev --ready-timeout 6000 --env PI_OFFLINE=1 --env PI_TELEMETRY=0 -- --provider openai --model gpt-6-sol` succeeded (exit **0**) and reported `worklane-pi ... is ready: it reads idle`. Native `list-agents --all` and `get-agent-state` agreed on a stable Pi `window_id`, `harness_id=pi`, `identity=report` and `state=idle`; the captured pane showed `gpt-6-sol`. This is genuine Pi hook **startup/idle**, not proof of model access: no credentials were mounted, no prompt was sent and no provider request was made. After a private `lane stop/start/open`, native `list-agents --all` restored the named Pi window with **`state=none`, empty `harness_id`** and did **not** restart Pi; the unwired policy correctly treats such a reserved pane as ambiguous and must not launch a duplicate. The private container was stopped after the probe. A further **credential-free, read-only identity check** restarted only that private container in the isolated VFS store, recreated its private `/run/user/1000`, started the saved TUIOS daemon and inspected the explicit `worklane-pi` window. `list-agents --all` still held the same reserved name, window ID and historical `agent_session_id`, but `state=none`/empty `harness_id`; `list-windows` still showed a Pi-looking title and a live window PID. Inside the private container, `/proc/<window-pid>/cmdline` was **`/bin/bash`**, and the scoped process list showed the TUIOS daemon and shell, **no Pi process**. Therefore neither persisted conversation ID, Pi-looking title, window ID, nor live shell PID establishes a running Pi or the required provider/model. A racing process could also appear later; Worklane must not automatically erase/relaunch this reserved window without atomic ownership/uniqueness and verified provider state. The exact private container was stopped after the check; no host auth was read or mounted. A second scratch lane using the final fixture's **exact image digest** (rather than the first probe's tag) also passed `create/open/stop` in the same private store and was stopped. The image remains only in the ignored v3 store. No default-store or `software_lab` container was changed.

**Still unverified:** handling forcibly terminated attach clients without an explicit target, provider override in a ready authenticated TUIOS pane (the user has separately verified Pi auth readiness), actual working/settled hook delivery, daemon-side uniqueness under concurrent start, safe recovery from a restored `state=none` pane, persistent process supervision, and isolated image **systemd boot**. A Pi *prompt* without credentials has not been tested in this lane. `lane start/open/attach` bootstrap a TUIOS shell and the hook, but the Pi supervisor policy is **not wired** to the CLI: agent launch was a one-time **manual test**, not automatic Worklane behavior. Do not route to Herdr or retry an ambiguous restored pane.
